名詞說明：

### 決策卡 I101-C1：R-VER-2 是否依嚴重度放寬

- **問題：** 同一機制連續兩輪都要修，而最新一輪只剩 NIT 時，修正迴圈要不要停下來等你決定？
- **為什麼要你決定：**
  - R-VER-2 的停止規則比 Core 嚴格。Core `workflow.md:72` 只要求重新評估，並寫明「並非自動停工」。
  - 這條停止規則來自你的 D-013 第 5 項與 PR-B 卡 1 (a)（REQ-012）。
  - 放寬專案自己加嚴的規則，只能由你決定（`skills/dev-core/deltas.md:4-17`）。
- **選項：**
  - **(a) 有界放寬（建議）**
    - 做法：四個條件都成立時才不停下。
      1. 只有「同一機制」這個觸發條件成立。另一個觸發條件是「連續兩輪有新的 MUST-FIX 或 SHOULD-FIX」，它照舊會停。
      2. 最新一輪的每個審查與掃描都依 R-DEL-2 算數。每個 finding 照獨立 reviewer 自己給的嚴重度都是 NIT。沒有未解的疑慮、沒有未驗證的安全問題、沒有 reviewer 查不到的部分、沒有 `NOT_RUN`。
      3. 失敗是品質問題，不是規格、驗收條件或設計造成的問題。
      4. 同一個 PR 裡還沒用過這個例外。
    - 條件成立後的修法：
      - 修正方先做 floor check，需要時升級，先依 R-REV-4 分類，也可以決定「維持現狀」。
      - 修正只動每個 NIT 指到的文字，不新增事實句。
      - 審查紀錄寫下這次使用的輪次和機制，以及修正 diff（修改的檔案、前後的 tree ID、diff hash）。
      - 下一次回覆就告訴你這次用了例外。
    - 照舊執行：push 前的窄範圍獨立確認（R-REV-4）、R-REV-9 掃描、Merge Review。
    - 回到停止規則的情形：修正需要動到 NIT 指的文字以外，或之後同一機制又要修，就照停止規則停下，不論嚴重度。
    - 結果：PR #100 第 3 輪那種只剩 NIT 的情形，不必再開一張停止卡。
    - 風險：那一次 NIT 修正少了你的檢視。每個 PR 最多一次。
    - 成本：窄範圍確認照舊要跑一次審查。
  - **(b) 同 (a)，但只限紀錄檔裡的 NIT**
    - 做法：(a) 的條件再加一條：每個 NIT 都在紀錄檔裡，例如 plan、review 紀錄、log、CHANGELOG、REQ、design-proposal。NIT 若在規則或 reference 文字裡，照停止規則停下。
    - 結果：公開的規則文字沒有經過你檢視，就不會變。
    - 風險：PR #100 第 3 輪的修正有一處在 reference 檔，這一版不會讓那一輪不停。
    - 成本：同 (a)。
  - **(c) 不放寬**
    - 做法：R-VER-2 不變，只做 E1 與 E2。
    - 結果：只剩 NIT 時仍然停下，等你的卡。
    - 風險：沒有新增風險。
    - 成本：每次停下多一張卡，可能多一輪審查。
- **不列為選項的做法：** Issue 原文是「修正後由 Merge Review 涵蓋」。如果因此不做 push 前的窄範圍確認，會同時放寬 `dev-gate` 的 push gate（`skills/dev-gate/SKILL.md:77`），也可能違反 Core 的要求：`Fixed` 要附重審證據（`review-and-security.md:21`）。放寬 Core 一律是缺陷（`deltas.md:4-5`），所以不列。
- **建議：** (a)——它解決 Issue 的第 3 個缺陷，保留所有獨立審查，每個 PR 最多一次。
- **如果你不決定：** U3 不能開始。U1、U2 可以照常進行。
- **證據：**
  - 事實：
    - PR #100 實作審查第 3 輪：deep 審查 0 MUST-FIX、0 SHOULD-FIX、2 NIT；Security Diff Scan 0 MUST-FIX、0 SHOULD-FIX、2 NIT。
    - 那一輪仍照 R-VER-2 停下。你的回答是「IR3-C1 a」。
    - 之後主代理自己修了三處，並記錄行號更新和 diff hash，沒有做內容審查。
    - 來源：PR #100 第 1 則留言 "Gate record: read-backs of PR-3's own dispatches (writer session)" 第 26–33 行。
  - 推論：去掉窄範圍確認會放寬 `dev-gate`。這是我從 `skills/dev-gate/SKILL.md:77` 和 R-REV-4（`skills/dev-core/SKILL.md:125`）推得的。
  - 未驗證：沒有。

### 決策卡 I101-C2：完整性檢查用指令還是新腳本

- **問題：** 搜尋清單與共同修改規則，要用寫在規則裡的 `git grep`／`git diff` 指令，還是新增一個比對腳本？
- **為什麼要你決定：** 新腳本是 pack 裡新的可執行檔和機制（R-RIG-3），範圍和審查成本都會變大。
- **選項：**
  - **(a) 寫在規則裡的確定性指令（建議）**
    - 做法：
      - 搜尋固定在受審內容的 tree ID 上。
      - 每個字串、每個檔案各記一列命中數；exit code 1 代表沒有命中，其他值代表檢查失敗。
      - 每個節點檢查一次共同修改：改了 REQ 檔，同一節點就要在 `log.md` 加一列寫出它的 ID。
    - 結果：命中數和指令結果都是確定性的。每列的處置對不對，仍由 reviewer 判斷。
    - 風險：字串和指令會放進 shell 執行，所以規則要求執行前先在文字裡檢查字元。
    - 成本：只改規則文字。
  - **(b) 新增腳本，例如 `skills/dev-plan/scripts/sweep.py`**
    - 做法：腳本讀計畫裡的清單和表格，跑 `git grep` 並比對，也檢查共同修改；附測試和 `check_pack` 釘選。
    - 結果：連比對也自動化，字元檢查放在程式裡。
    - 風險：新的可執行檔要做 Security Diff Scan；計畫的格式會被腳本綁住。
    - 成本：一個腳本、測試和審查，可能要多輪。
- **建議：** (a)——PR #100 漏掉的是 `log.md` 的列，每個節點跑一次共同修改檢查就抓得到，腳本的獨特作用小。
- **如果你不決定：** U1 不能開始。
- **證據：**
  - 事實：
    - PR #100 實作審查第 2 輪的 SHOULD-FIX IR2-P3-D-01：P3-T3 改了 REQ-009，但 `log.md` 沒有對應的列（`.dev/issue-96-pr3/plan.md:303-305`）。
    - 兩輪逐列比對都對上：166／166（`:277`）、186／186（`:326`）。
  - 推論：P3-T3 的 diff 裡沒有一列寫出 REQ-009，所以每個節點的共同修改檢查會失敗。這是依 d2 E1.2 的寫法推得的，還沒有實際對 P3-T3 的 tree 跑過。
  - 未驗證：P3-T3 前後的 tree ID 沒有紀錄，現在無法重跑這項檢查。

### 決策卡 I101-C3：審查單位與 PR

- **問題：** 三個切片要各自成為一個審查單位、在同一個 PR 裡依序做，還是用別的分法？
- **為什麼要你決定：**
  - `dev-plan` 第 6 步規定：strict 目標的每個切片各是一個審查單位（`skills/dev-plan/SKILL.md:96-97`）。
  - 判斷 PR 要不要拆，由你決定。
- **選項：**
  - **(a) 三個單位、一個 PR（建議）**
    - 做法：依序做 U1（E1）、U2（E2）、U3（E3）。每個單位的實作審查（deep＋Security Diff Scan）通過、commit 之後，才開始下一個。
    - 結果：符合規則，放寬的部分單獨審查，一個 PR 關閉 #101。
    - 風險：三個單位共用 `deltas.md`、REQ 檔和 CHANGELOG，後面的單位會改到前面改過的檔案。
    - 成本：三次實作審查、一次 Merge Review。
  - **(b) 三個 PR**
    - 做法：每個單位各開一個 PR。
    - 結果：可以分開回退。
    - 風險：多兩次 merge 和 Merge Review。
    - 成本：最高。
  - **(c) E1＋E2 合成一個單位（規則的例外）**
    - 做法：U1 = E1＋E2，U2 = E3。
    - 結果：少一次審查。
    - 風險：違反 strict 的單位規則，要你明確同意這個例外。E1 新增要執行的指令，風險不比 E2 低。
    - 成本：兩次實作審查。
- **建議：** (a)。
- **如果你不決定：** 實作不能開始。
- **證據：**
  - 事實：`skills/dev-plan/SKILL.md:96-97`。
  - 推論：E1、E2、E3 互相獨立，可以各自審查。

### 決策卡 I101-C4：沒標來源、但內容正確的事實句算什麼

- **問題：** 新寫的事實句沒有標來源或「推論」「未驗證」，但內容是對的，審查時要算 NIT finding，還是記成 residual risk？
- **為什麼要你決定：** R-REV-3 的嚴重度門檻來自你的 D-013 第 1 項（REQ-012）：NIT 只限退化或不實的文件，門檻以下列為 residual risk。把這種句子算成 NIT，等於改了你的決定。
- **選項：**
  - **(a) 照門檻記成 residual risk，commit 前由寫的人補上（建議）**
    - 做法：
      - reviewer 把這些句子列在報告的 residual risk。
      - 主代理在 commit 前補上來源或標記，由下一輪審查或窄範圍確認核對。
      - 內容錯的句子照舊至少算 NIT。
    - 結果：門檻不變，缺來源的句子仍然會在 commit 前補上。
    - 風險：補上這件事靠管理措施執行，不靠 gate。
    - 成本：低。
  - **(b) 算成 NIT finding**
    - 做法：R-REV-3 加一種 NIT：「新事實句沒有來源或標記」。
    - 結果：一定要給 disposition，gate 也看得到。
    - 風險：改了 D-013 第 1 項。紀錄精確度的 NIT 會變多，也會更常用到卡 C1 的例外。
    - 成本：可能多出審查輪次。
- **建議：** (a)——不改你既有的門檻，而且 PR #100 那次錯的條件屬於內容錯誤，本來就算 finding。
- **如果你不決定：** U2 不能開始。
- **證據：**
  - 事實：`skills/dev-core/SKILL.md:113-117`（嚴重度門檻）；`docs/requirements/REQ-012-review-convergence.md:11`（D-013 第 1 項引文）。
  - 推論：兩位 reviewer 都認為，把這種句子算成 finding 會繞過門檻（DR1-07、SR1-08）。
