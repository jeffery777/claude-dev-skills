# Push scan (R-REV-9)

This file is part of rule R-REV-9 of `dev-core`. The main agent and the reviewer
follow the steps below.

- Before a push:
  1. The main agent (not the read-only reviewer) checks the configured remote names without substituting them: `git remote | LC_ALL=C grep -Evx '[A-Za-z0-9._][A-Za-z0-9._-]*'` prints nothing, and `<remote>` is one of those names.
  2. The main agent checks, without printing the URLs, that the fetch and push URLs of `<remote>` are one and the same: `test "$(git remote get-url --all '<remote>' 2>/dev/null)" = "$(git remote get-url --push --all '<remote>' 2>/dev/null)" && test "$(git remote get-url --all '<remote>' 2>/dev/null | wc -l)" -eq 1 && test "$(git remote get-url --push --all '<remote>' 2>/dev/null | wc -l)" -eq 1 && echo PASS || echo STOP` prints `PASS`. The command sends the error output to `/dev/null`, because the error output can show the user name and host of the URL (for example a `transfer.credentialsInUrl` warning); the command counts each URL list, because `$(…)` drops trailing newlines. No URL goes into a brief or a record.
  3. The real push has only this form: `git push --no-recurse-submodules`, then any of `--set-upstream`, `--tags`, `--follow-tags` and `--all`, then `'<remote>'` and the refspecs. It names `'<remote>'` explicitly, so `remote.pushDefault` and `branch.<name>.pushRemote` choose no other remote; it has no other option and nothing between `git` and `push`; and it runs in the same worktree and environment as the checks and the dry-run (no `GIT_*` variable set for only one of them). An option after the refspecs counts as an option too; a force or delete option or refspec (`--force`, `--force-with-lease`, `--delete`, a `+` prefix, an empty source) is outside this form. Configuration (`remote.<name>.push`, `remote.<name>.mirror`) can still make a push of this form force or delete. The configuration check below stops such a push before the dry-run. The dry-run shows a remaining force or delete as a `+` or `-` ref line, which fails step 4 (step 5 then stops the push). A submodule push is a separate push with its own scan. Write each refspec source as a full ref name, for example `refs/heads/<branch>:refs/heads/<branch>`; step 7 blocks `HEAD` and abbreviated object IDs (the dry-run prints a short branch or tag name as its full name). Before the dry-run, the main agent checks the configuration of `<remote>` (the result does not depend on the remote state): `git config --type=bool --get 'remote.<remote>.mirror'` does not print `true`, and `git config --get-all 'remote.<remote>.push' | LC_ALL=C grep -E '^[+]|^:.'` prints nothing (a `+` refspec forces; `:<dst>` deletes). The main agent runs `git ls-remote --heads --tags '<remote>'` (no `git fetch`) and the real push command with `--dry-run --porcelain` added after `push`. The error output of `ls-remote`, the dry-run and the push can show the user name and host of the URL (for example a `transfer.credentialsInUrl` warning or an access error); none of it goes into a brief, a record or a post. The dry-run exits 0, its last line is `Done`, and it lists at least one tab-separated ref line.
  4. Before a name from the dry-run goes into any command, the main agent checks the tab-separated ref lines of the saved dry-run output without substituting names: `awk -F'\t' 'NF >= 3 && split($2, a, ":") != 2' <dry-run output>`, `awk -F'\t' 'NF >= 3 {print $2}' <dry-run output> | tr ':' '\n' | LC_ALL=C grep -Evx '[A-Za-z0-9._/-]*'` and `awk -F'\t' 'NF >= 3 && ($1 == "+" || $1 == "-")' <dry-run output>` print nothing (a `+` line is a forced update, a `-` line a delete).
  4a. The main agent runs `python3 -I ${CLAUDE_SKILL_DIR}/../dev-core/../dev-gate/scripts/push_precheck.py verify --dry-run <saved dry-run output> --remote-ids <file with the step-6 ID list>` in the worktree of the dry-run (it first produces that list with the command of step 6). The script runs the source checks of step 7 with an exit-code check for every Git call. Exit 2 or any result other than 0: stop (step 5). Exit 0 does not replace any scan: steps 6 to 8 always run, and the reviewer still runs step 7 and scans everything the push sends (Issue #68, fallback (c)).
  5. When a check in steps 1 to 4 fails or step 4a stops, or the scan of step 8 reports a blocking signature finding, or the push needs another form, the main agent stops and asks the user; a force push or a delete is a separate decision of the user. For a signature, the user decides whether the identity of the signing key may be published. When the user allows it, the main agent records the signature finding with the disposition `Rejected`, with the user's answer as the source and the reason. The answer covers only the commits and tags of this scan and this push. When the scan has no other open finding, the R-REV-9 scan counts as passed, and the main agent continues at step 9. The user may change the names, the configuration or the push; after any change, the main agent starts again at step 1, and the scan of what the push sends is never skipped.
  6. The brief gives the tab-separated ref lines of the dry-run (not its `To` line, which can hold the URL) and the object IDs that `ls-remote` lists (`git ls-remote --heads --tags '<remote>' | cut -f1 | grep -Ex '[0-9a-f]{40}|[0-9a-f]{64}' | sort -u`).
  7. The reviewer runs its commands in the worktree where the dry-run ran, which the brief names. It reports a blocking finding when the dry-run list in the brief has no tab-separated ref line. For each tab-separated ref line of the dry-run except `=` (up to date) and `-` (deleted), the reviewer takes the source, left of `:`, as `<source>`. Before it puts a value from the brief into a command, it checks the value in the brief text, not with a command that contains the value: each ID matches `[0-9a-f]{40}` or `[0-9a-f]{64}`, and `<source>` matches `[A-Za-z0-9._/-]+`. Otherwise it reports a blocking finding and does not run the command. It reports a blocking finding unless `<source>` starts with `refs/heads/` or `refs/tags/` or is a full hexadecimal object ID (other `refs/` names, such as `refs/bisect/` or `refs/worktree/`, can differ per worktree), and `git --no-replace-objects cat-file -t '<source>'` prints `commit`, or prints `tag` while line 2 of `git --no-replace-objects cat-file -p '<source>'` is `type commit`. When the third field of the line starts with `<old>..<new>` or `<old>...<new>` (a forced update), it reports a blocking finding unless `<old>` is the start of an ID in the brief (otherwise the push can go to another repository than the one `ls-remote` read); a new ref has no old value to check.
  8. The reviewer scans every commit the remote does not have yet, with identities, messages, the commit headers other than `encoding` (Git converts the message to UTF-8 and drops that header) and merge-resolution content: `printf '%s\n' <IDs> | git --no-replace-objects cat-file --batch-check='%(objectname) %(objecttype)' | awk 'NF == 2 && $2 != "missing" {print "^" $1}' | git --no-replace-objects -c core.quotePath=false log --format=raw --no-mailmap --no-show-signature --encoding=UTF-8 --root --no-relative -p --cc --text --no-textconv --no-ext-diff --ignore-submodules=none --stdin '<source>'`. For each `<source>` that is a tag, it scans the tagger and message with `git --no-replace-objects cat-file -p '<source>'`. A commit signature is a line of the scan view that starts with `gpgsig `, `gpgsig-sha256 ` or `mergetag ` (a commit header; the view indents message lines by four spaces). A tag signature is a line of a scanned tag that starts with `gpgsig` or `-----END `, or contains `-----BEGIN ` (a message without a trailing newline puts the signature block inside the last message line). A signature on a merge or squash commit that the hosting platform created (committer `GitHub <noreply@github.com>`) is recorded only: the reviewer lists it without a blocking finding. For every other signature, the reviewer reports a blocking finding with the disposition Needs Human Decision. The finding lists each signed commit or tag and the kind that the `-----BEGIN` line names (for example `PGP SIGNATURE`, `SSH SIGNATURE`, or `SIGNED MESSAGE` for x509). The reason: a signature can carry a name or email that the headers do not show (the certificate of an x509 signature, the signer's user ID of an OpenPGP signature). The reviewer does not decode the signature. The deterministic checks are the log command of this step piped into `LC_ALL=C awk '/^commit /{c=$2} /^(gpgsig|gpgsig-sha256|mergetag) /{print c, $1}'`, which prints the header of each signed commit and, unless color output is forced, its ID, and for a tag `git --no-replace-objects cat-file -p '<source>' | LC_ALL=C awk '/^gpgsig|-----BEGIN |^-----END /'`; output means a signature.
  9. After the scan, the main agent pushes with exactly the arguments of the dry-run, without `--dry-run --porcelain`, and changes no ref, configuration or remote between step 1 and the push.

Not covered: the scans cover the commands and checks above. They do not cover the following, which the user accepted as residual risk (FU-015 cards 1a and PR1-C1a, and card PR2-C1a; card RB-C3a of Issue #52; cards FU017-C1b and FU017-R1-C1a of Issue #54): the same URL served by another program, helper, ssh wrapper or proxy (`remote.<name>.receivepack`, `remote.<name>.uploadpack`, `remote.<name>.vcs`, `<transport>::` URLs, `core.sshCommand`, `GIT_SSH*`); a configuration, ref or remote change between step 1 and the push that the main agent did not make; for the configuration check of step 3, which reads only the repository configuration that `git config` shows: the `GIT_CONFIG` environment variable, legacy `$GIT_DIR/remotes/` and `$GIT_DIR/branches/` files, and Git versions before 2.18 (no `--type`); per-ref read permissions of a hosting platform; a hook, for example pre-push, which runs during the dry-run and the push and can add lines to the dry-run output, or reference-transaction during the push; the decoded content of signatures, which the scans report but do not read (step 8, card FU017-C1b of Issue #54); signatures that the platform adds when it creates a merge or squash commit; push options and Git LFS objects (FU-007), and push certificates; a false `encoding` header (an ordinary `git commit` with `i18n.commitEncoding` set writes one for UTF-8 text): the push scan does not show the header value, and text that Git cannot convert stays unconverted; an `encoding` header that names an encoding that is not ASCII-compatible (for example UTF-16 or EBCDIC): Git converts the headers too, and the view can show no readable identity or signature header; a NUL byte in an object; bytes that are not UTF-8 in names or messages; and invisible or bidirectional Unicode characters, which `core.quotePath=false` shows as raw bytes. The threat model of REQ-011 says why deliberately malicious configuration and hooks are outside R-REV-9.
